# SafeBed Geospatial Search & Navigation Safety v0.1

**Status:** public discovery architecture using synthetic examples only. This document does not select a map/geocoder/routing vendor, freeze a geospatial API, approve live protected-location processing or replace a DPIA/safeguarding review.

SafeBed needs to answer a spatial question — **what suitable help can this person practically reach?** — without turning location technology into a new disclosure channel for either the person seeking help or a protected accommodation service.

The governing rule is:

> **A protected exact coordinate must be excluded before data crosses an unauthorised trust boundary. Hiding a marker after the coordinate has reached the browser or a third party is not protection.**

---

## 1. Non-negotiable invariants

1. Public discovery never receives an exact protected destination.
2. A protected destination is a separate resource from public service discovery.
3. The browser receives only geometry authorised for that browser/user/placement state.
4. A third-party tile, geocoding, routing, analytics, crash-reporting or session-replay service must never receive a protected coordinate merely because SafeBed itself is authorised to hold it.
5. Search origin/location is collected at the minimum precision necessary and is not retained as routine movement history.
6. No background tracking, geofencing or continuous phone location is required to find, travel to or confirm arrival at accommodation.
7. The accessible list is complete; the map is supplementary.
8. A stale bed count cannot become live merely because cached map/service information remains available.
9. Approximation must be intentionally safe. Randomly jittering a protected coordinate is not an acceptable disclosure control.
10. External navigation is a disclosure event, not just a UI convenience.

---

# 2. Separate the spatial data classes

SafeBed should not use one generic `location` object for every purpose.

## 2.1 Search origin

The place from which a person/supporter is searching.

Possible forms:

- `AREA_QUERY` — town, postcode district or other human-entered area;
- `APPROXIMATE_ORIGIN` — coarse position sufficient for nearby ranking;
- `PRECISE_ORIGIN` — device/user coordinate where the person explicitly chooses this and the additional precision is genuinely useful.

Search origin is **ephemeral matching input**, not a case-history field by default.

A future implementation should prefer an area/coarse origin when that is sufficient.

## 2.2 Public service geography

Information intentionally safe to disclose during discovery.

Examples:

- public exact service point;
- intentionally published public service area;
- deliberately coarse safe area/region;
- public human-readable area label;
- no geometry at all.

## 2.3 Protected destination

The actual arrival destination for accommodation whose exact location requires authorisation.

This is not embedded inside a public service object.

It may include:

- exact address;
- exact coordinate;
- arrival instructions;
- protected contact/travel information.

It is returned only through the authorised placement/disclosure path.

---

# 3. Public map projection

The browser should receive a derived **public map projection**, never an internal provider-location record.

Conceptually a result can be projected into one of:

### `PUBLIC_POINT`

The provider explicitly permits the exact public location to be shown.

The browser may receive the public coordinate.

### `SAFE_AREA`

The provider permits an intentionally safe coarse area or polygon to be shown.

The geometry must be separately supplied/approved as safe public information. It must **not** be generated by taking the protected address and applying a small random offset.

### `NO_GEOMETRY`

The service remains discoverable in the list but no spatial shape is returned to the public client.

The UI may say, for example:

> Location protected — referral required.

rather than silently dropping the service.

## Relationship to SafeBed disclosure classes

SafeBed's `PUBLIC`, `VERIFIED_USER`, `PLACEMENT_AUTHORISED`, `RESTRICTED` and `SEALED` classes remain authorisation classifications.

Map projection is an output of those policies, not a new universal disclosure hierarchy.

A `RESTRICTED` service may still have a separately approved `SAFE_AREA`; it never follows that the actual restricted coordinate may be sent to the public map.

---

# 4. Server-side search pipeline

A safe future architecture is conceptually:

```text
BROWSER
  ↓
minimum necessary search origin
  ↓
SAFEBED SEARCH SERVICE
  ↓
transient geocoding/normalisation where required
  ↓
SERVER-SIDE spatial candidate search
  ↓
provider eligibility + availability + access-pathway matching
  ↓
disclosure/map-projection policy
  ↓
PUBLIC-SAFE RESULT PAYLOAD
  ↓
BROWSER LIST + SUPPLEMENTARY MAP
```

The server may need protected internal geography to establish that a service is relevant to an area.

That does **not** mean the result may reveal the coordinate used internally.

---

# 5. Distance and triangulation

Exact distance can itself disclose location.

For an ordinary public service, a precise/rounded distance may be useful and acceptable subject to ordinary privacy review.

For a protected service, SafeBed must not return a numeric distance derived from the protected exact coordinate to an unauthorised caller.

Otherwise repeated searches from different origins can become a triangulation oracle even when the marker itself is hidden.

Safer public possibilities include:

- no distance at all;
- a provider-approved area label;
- a deliberately coarse accessibility/travel statement derived from a **safe public area**, not from the protected point;
- referral-pathway wording without spatial detail.

Repeated probing, unusually precise origins and automated enumeration should also be considered in rate/abuse controls for sensitive service discovery.

---

# 6. Geocoding the search origin

A user typing a town/postcode and a user sharing a precise device coordinate create different privacy risks.

Before selecting a geocoder, SafeBed must decide:

- what precision is actually necessary;
- whether the query can be resolved using a locally held/public geographic dataset;
- whether an external processor receives the raw query/origin;
- what that processor logs/retains;
- whether the request is associated with SafeBed/user identifiers;
- what contractual/DPIA controls apply;
- what happens when the geocoder is unavailable.

A precise origin must not be copied into analytics, ordinary application logs or a long-lived referral record merely because geocoding occurred.

---

# 7. HTTP/query-string boundary

Precise origins and protected destinations should not be placed casually in URLs.

URLs may leak through:

- browser history;
- reverse-proxy/access logs;
- referrer headers;
- screenshots/copy-paste;
- monitoring;
- support diagnostics.

The current v0.2 `GET /v1/services/search?area=...` remains deliberately vague/public-safe and does **not** freeze a future precise-coordinate search API.

If a future search accepts precise origin data, the API method/body/logging/cache design must be reviewed specifically for that data class.

Protected destination responses should use appropriate no-store/referrer controls and must not encode the destination in shareable query strings.

---

# 8. Map tiles and browser requests

A map library is not just pixels.

A browser may contact external origins for:

- JavaScript;
- styles;
- vector/raster tiles;
- glyphs/fonts;
- sprites/icons;
- telemetry;
- geocoding;
- routing.

Tile requests reveal the map viewport to the tile provider. That may be acceptable for ordinary public geography after review, but it becomes dangerous if the map is centred/zoomed specifically around a protected exact destination.

Therefore:

- protected exact destination coordinates must not drive unauthorised third-party tile requests;
- remote analytics/session replay must not receive map/location state;
- production Content Security Policy should restrict network origins deliberately;
- self-hosting/proxying may be considered where it materially reduces disclosure, but is not assumed automatically to be the best option;
- provider terms/licensing/caching requirements must be reviewed before implementation.

---

# 9. Navigation is a disclosure action

SafeBed should separate four travel cases.

## 9.1 Public destination

Provider permits public address/coordinate disclosure.

SafeBed may offer ordinary walking/transit/driving hand-off subject to product/provider policy.

## 9.2 Placement-authorised destination

Exact destination is available only after the caller/placement satisfies server-side authorisation.

SafeBed may then display travel instructions, but must separately decide whether handing the destination to an external navigation provider is permitted.

## 9.3 Restricted specialist destination

Default assumption: **do not automatically send the destination to a third-party navigation service**.

The provider/specialist pathway may instead require:

- provider-controlled instructions;
- a meeting/pick-up point;
- authorised worker hand-off;
- transport arranged without exposing the final address to the ordinary client/application provider.

External routing is permitted only if the relevant safeguarding/data-governance policy explicitly allows that disclosure.

## 9.4 Sealed destination

Ordinary SafeBed client APIs do not receive the destination.

Navigation remains entirely in the specialist/provider-controlled process.

---

# 10. Destination response security

When an exact protected destination is legitimately disclosed:

- authorisation is derived server-side;
- placement/resource state is checked at request time;
- the disclosure is auditable;
- the response is not cached publicly;
- sensitive fields are excluded from ordinary logs/traces;
- browser/service-worker persistence is deliberately controlled;
- a revoked/changed placement must prevent future reads;
- share/export behaviour is explicit rather than automatic.

A previous authorised read cannot always be made unknowable to the human/browser afterward, so the product must minimise persistence and make the disclosure event itself intentional.

---

# 11. Caching and service workers

The future PWA may cache public/static service information for weak connectivity.

It must not silently cache:

- protected exact destinations;
- precise search-origin history;
- sensitive referral payloads;
- a previously live capacity response and later present it as current.

A service worker must use explicit cache classes rather than a blanket `cache-first` strategy.

Suggested conceptual classes:

- `PUBLIC_STATIC` — potentially cacheable;
- `PUBLIC_SERVICE_METADATA` — cacheable under bounded freshness rules;
- `LIVE_AVAILABILITY` — network/current-state rules; never silently promoted from stale cache;
- `PERSONAL_REFERRAL` — private/no ordinary offline cache unless explicitly designed and approved;
- `PROTECTED_DESTINATION` — `no-store` by default.

---

# 12. Logging, observability and analytics

Location leaks often happen outside the product database.

Production review must cover:

- HTTP access logs;
- reverse proxy/ingress logs;
- application logs;
- distributed tracing;
- exception/crash reports;
- metrics labels;
- analytics;
- session replay;
- support tooling;
- CDN/WAF logs.

Rules:

- never use exact coordinate/address/referral text as metric labels;
- redact sensitive request/response bodies from observability;
- avoid recording precise origins by default;
- disable session replay on sensitive workflows unless a future governance decision can justify a privacy-safe implementation;
- do not log protected destination payloads to prove they were returned — log the authorised disclosure event/identifiers instead.

---

# 13. Sharing directions

A useful feature may be **send directions to the person's phone** or share with a supporter.

That is not automatically safe.

A future share mechanism must distinguish:

- public directions — ordinary share may be acceptable;
- protected destination — requires an authorised, short-lived/minimised hand-off;
- restricted/sealed destination — may prohibit ordinary share entirely.

Do not put a protected address into a long-lived public URL or unrevocable unauthenticated token merely for convenience.

---

# 14. Weak-signal behaviour

When connectivity degrades:

SafeBed may retain:

- public service name/contact route where permitted;
- static public area/opening information;
- previously downloaded non-sensitive UI assets.

SafeBed must not claim:

- cached capacity is live;
- an expired hold remains active;
- a reservation still exists when current state cannot be confirmed.

For an already confirmed placement, offline travel support requires a separate decision about what authorised destination/instructions may remain on-device and for how long.

No continuous location tracking is required.

---

# 15. Accessibility

The map is supplementary.

Every result represented on a map must have equivalent meaningful information/action in the list/workflow.

Do not require:

- visual marker discrimination;
- colour alone;
- drag/pinch gestures;
- spatial map interpretation

in order to find or act on accommodation information.

The existing SafeBed list/map keyboard and Accessibility Tree work remains the baseline when real mapping is introduced.

---

# 16. Synthetic data model for future proof work

Before choosing a mapping implementation, a synthetic test harness should distinguish:

```text
InternalServiceLocation
  exactDestination?       // server/protected store only
  safePublicProjection?   // explicitly approved independent geometry
  disclosureLevel
  externalRoutingPolicy

PublicMapProjection
  PUBLIC_POINT | SAFE_AREA | NO_GEOMETRY
  geometry?               // only public-safe geometry
  publicAreaLabel

AuthorisedDestination
  returned only after server-side resource/state/identity policy
```

The actual API names are intentionally **not frozen by v0.1 of this document**.

---

# 17. Synthetic proof requirements

Before real map integration, automated tests should prove at least:

1. `PublicService` remains free of exact destination/address/coordinate fields.
2. A restricted synthetic provider's exact coordinate cannot appear anywhere in anonymous discovery JSON.
3. Map projection for protected service uses only explicitly supplied safe geometry or no geometry.
4. Safe-area geometry is not calculated by jittering the protected exact point.
5. Public response never returns a numeric distance derived from a protected exact point.
6. List ↔ map switching cannot reveal additional protected data.
7. A browser-controlled role/disclosure parameter cannot expose destination.
8. Protected destination requires server-side placement/identity/resource policy.
9. A revoked/suspended relationship prevents future destination reads.
10. External-routing policy for restricted/sealed services defaults to provider-controlled/no external hand-off.
11. Protected coordinates are absent from URLs, analytics fixture payloads and ordinary logs in the test architecture.
12. Live availability/offline regressions remain fail-safe.
13. Narrow/reflow/keyboard/accessibility regressions remain green.

---

# 18. Threat table

| Threat | Unsafe design | Required SafeBed control |
| --- | --- | --- |
| Hidden marker leak | Send exact coordinate, hide CSS marker | Never send protected point to unauthorised client |
| Browser devtools leak | Protected address in JSON state | Separate protected destination resource |
| Triangulation | Return precise distance to hidden point | No distance derived from protected point for public caller |
| Jitter reversal | Randomly offset refuge marker | Explicit provider-approved safe area or no geometry |
| Tile-provider leak | Centre external tiles on restricted address | Do not route unauthorised protected point to tile service |
| Routing-provider leak | Auto-open external directions to refuge | Policy-controlled routing; provider hand-off available |
| Log leak | Query-string lat/lon/address | Minimise URL use, redact/log identifiers only |
| Analytics leak | Send search/destination coordinates as events | Exclude location/protected state from analytics |
| Offline leak | Service worker caches destination | `PROTECTED_DESTINATION` no-store default |
| Stale access | Old placement can still fetch location | Re-authorise each protected read against current state |
| Share-link leak | Permanent unauthenticated directions URL | public-only sharing or short-lived authorised hand-off |

---

# 19. Provider / technology evaluation criteria

A later map/geocoder/router evaluation should compare candidates on at least:

- what exact request data leaves SafeBed;
- request/telemetry logging and retention;
- ability to disable telemetry;
- UK GDPR/data-processing terms and hosting/subprocessor model;
- public vs protected-location compatibility;
- offline/low-bandwidth support;
- accessibility;
- UK walking/transit coverage where relevant;
- rate limits/cost sustainability for a public-good service;
- licensing/attribution/cache requirements;
- self-host/proxy options where useful;
- operational reliability;
- ability to avoid embedding secret API credentials in a public client.

The cheapest or most familiar map library is not automatically the safest architecture.

---

# 20. Stop conditions

Do not introduce a real map/geocoder/router into a live-data SafeBed flow if:

- protected coordinates must be sent to the public browser to make the map work;
- a third party would receive protected destinations without explicit governance/provider approval;
- precise search-origin data is retained/logged without a defined need;
- protected distance output creates a practical triangulation route;
- mapping cannot be used without session replay/analytics receiving sensitive state;
- destination responses are publicly/cacheably exposed;
- the identity/authorisation layer is still client-controlled;
- provider safeguarding rules for routing/meeting points are unknown;
- DPIA/data-flow review has not covered the mapping processors and logs.

---

# 21. Relationship to other SafeBed work

This architecture builds on but does not replace:

- **Availability Protocol/OpenAPI v0.2** — public service has no exact protected destination;
- **identity/authorisation work** — protected reads are server-derived from verified state;
- **live-use governance gates** — mapping/geocoding/routing data flows belong in the DPIA/data-flow register;
- **UX accessibility work** — list is complete and map supplementary;
- **provider discovery** — actual address/routing disclosure rules must come from providers/specialist safeguarding practice.

The first implementation milestone is therefore not “add Mapbox/Google/OSM”.

It is:

> **Prove with synthetic data that SafeBed can rank nearby options and render a useful public map while the restricted provider's exact coordinate is absent from every unauthorised client/third-party payload.**
